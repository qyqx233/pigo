# SPEC: 服务端状态入库（SQLite 默认，支持 PostgreSQL）

- 状态：v2 已实现（2026-09-19）：对话内容为 JSONL，账本按一轮缓存提交，见第 7 节（与前文冲突处以第 7 节为准）。SQLite 已完整验证；PostgreSQL 的实现与测试已就绪，尚未在真实 PostgreSQL 上运行（设置 PIGO_TEST_POSTGRES 后可跑）
- 范围：`cmd/pigo-server`。不改上游 `internal/`；上游记忆功能自己的 SQLite 文件不受影响。

## 1. 目标

1. 服务端的全部持久状态存进数据库：用户与登录、设置（含价格表和自定义 provider）、密钥、自定义模型、会话元数据与一轮的状态、transcript、计费账本。只有真实文件（工作区、沙箱 home、运行目录、沙箱日志）留在磁盘。
2. 默认 SQLite（数据目录下的 `pigo.db`），可选 PostgreSQL。
3. 解决现有问题：transcript 每步整体重写、时间戳每次被重写；账本统计每次扫全月文件；`meta.json` 等小文件频繁整体重写。

## 2. 已确认的决定

| 项目 | 决定 |
| --- | --- |
| 入库范围 | 全部服务端状态 |
| 数据库 | SQLite（`modernc.org/sqlite`，已在依赖里）+ PostgreSQL（`pgx`），都是纯 Go，`CGO_ENABLED=0` 不受影响 |
| 访问层 | `database/sql` + 手写 SQL + 很薄的方言适配 |
| 多实例 | 不支持。启动时加实例锁，第二个实例拒绝启动 |
| 旧数据 | `pigo-server migrate` 手动迁移；启动时发现未迁移的旧文件则拒绝启动并提示；迁移成功后旧文件移到 `legacy/` |
| 库间搬迁 | 本期不做 |
| 配置 | `-db` 参数或 `PIGO_DB` 环境变量；省略时为 `<data>/pigo.db` |
| transcript | 每条消息一行；每步只插入新消息；压缩等改写历史时在一个事务里整体替换 |
| 结构升级 | 内嵌编号 SQL 脚本，启动时执行未跑过的 |
| 测试 | SQLite 每次都跑；设置 `PIGO_TEST_POSTGRES` 时对 PostgreSQL 再跑一遍 |

## 3. 设计

### 3.1 连接与方言

- 连接串：`sqlite:<路径>`（`sqlite:///abs/pigo.db` 或 `sqlite:pigo.db`，相对路径相对于数据目录）、`postgres://…` / `postgresql://…`。
- SQL 统一写 `?` 占位符，PostgreSQL 下改写为 `$1…$n`。
- upsert 两者都支持 `INSERT … ON CONFLICT (…) DO UPDATE SET x = excluded.x`，无需分支。
- 类型取两者的公共子集：`TEXT`、`BIGINT`、`INTEGER`、`DOUBLE PRECISION`。时间一律存 UTC 的 Unix 纳秒（`BIGINT`），可比较、可排序、两边一致。结构化但无需查询的字段存 JSON 文本。
- 主键都由应用生成（随机 ID 或 `(会话, 序号)`），不依赖各库不同的自增语法。
- SQLite：WAL 模式、`busy_timeout`、单连接（写入串行，避免 `SQLITE_BUSY`）。

### 3.2 实例锁

- SQLite：对 `<db 文件>.lock` 加独占 `flock`，进程退出自动释放。
- PostgreSQL：在一条固定连接上持有 `pg_try_advisory_lock`。
- 拿不到锁即拒绝启动："另一个 pigo-server 正在使用这个数据库"。

### 3.3 表结构（v1）

| 表 | 内容 | 说明 |
| --- | --- | --- |
| `schema_migrations` | 已执行的脚本版本 | 迁移器维护 |
| `users` | 账号 | `username_key` 唯一 |
| `auth_sessions` | 登录令牌（只存哈希） | 按用户索引 |
| `credentials` | `(owner, provider)` → 加密记录 | owner 为空表示公共；加密方式不变 |
| `settings` | `name` → JSON 文档 | 目前一行 `server`：默认模型、开关、自定义 provider、价格表。低频配置整体存取，结构演进不需要改表 |
| `custom_models` | 自定义模型 | `(scope, user_id, id)` 主键 |
| `sessions` | 会话 | `id`、`user_id` 两列加整份元数据 JSON（含 `activeTurn` / `lastTurn`） |
| `messages` | transcript | `(session_id, seq)` 主键；`entry_id`、`at`、消息 JSON（上游格式原样） |
| `ledger` | 计费账本 | 每次调用一行；按 `session_id`、`(user_id, at)`、`at` 建索引 |

删除会话删除 `sessions` 和 `messages` 中的行，账本保留（与现有决定一致）。

### 3.4 存储层接入方式

单实例下，各个存储保留现有的内存结构和对外方法，只把持久化从"整份写 JSON 文件"换成"按行写库"：

- 用户、登录、密钥、设置、自定义模型：启动时从库加载到内存；每次修改只写受影响的行（插入 / 更新 / 删除），写库失败则回滚内存修改，与现在的行为一致。
- 会话元数据：`saveMeta` 改为对 `sessions` 表 upsert 一行。
- transcript：会话记住已落库的消息条数和最后一条的内容。每步存档时，如果已落库的最后一条没有变化，就只插入新消息；否则（压缩、异常）在一个事务里整体替换。
- 账本：写入即插入；报表按条件 `SELECT`（走索引），聚合仍在 Go 里做，报表逻辑不变。

### 3.5 迁移命令

```
pigo-server migrate [-data <目录>] [-db <连接串>]
```

1. 目标库必须为空（没有用户、会话、账本），否则拒绝，防止重复导入。
2. 在一个事务里导入：`auth/auth.json`、`settings.json`、`credentials.json`、`models/models.json`、每个会话的 `meta.json` 与 transcript（保留原有的消息 ID 和时间戳）、`ledger/*.jsonl`。
3. 提交成功后，把这些文件移到 `<data>/legacy/`，保持原来的相对路径；工作区等真实文件不动。
4. 打印各类数据的导入条数。

服务启动时如果数据目录里还有上述旧文件，就拒绝启动，并提示先运行迁移命令。

## 6. 实现细化（编码前核实代码后的结论）

### 6.1 各存储的写法

| 存储 | 现有文件 | 内存结构 | 改为 |
| --- | --- | --- | --- |
| 用户与登录 | `auth/auth.json` | 保留 | 注册：插入用户和登录令牌（一个事务）；登录：删除过期令牌并插入新令牌；登出：删一个令牌；停用、重置密码：更新用户并删除其全部令牌；删除用户：删用户和令牌。**先写库，成功后再改内存**，写库失败时内存不变（顺带修掉现在"写文件失败但内存已改"的几处） |
| 密钥 | `credentials.json` | 保留 | `set` upsert 一行，`delete` 删一行，`dropUser` 按 owner 删。没有配置 `PIGO_SERVER_SECRET` 时仍然停用：不读、不写，库里的行保持原样 |
| 设置 | `settings.json` | 保留 | `settings` 表中名为 `server` 的一行，整份 JSON upsert。没有这一行时用启动参数给的默认值，且不写库（与现在一致） |
| 自定义模型 | `models/models.json` | 保留 | `add` upsert，`remove` 删一行，`dropUser` 按用户删。加载按 `created_at, id` 排序，保持原来的插入顺序 |
| 会话元数据 | `sessions/<id>/meta.json` | 保留（`managedSession.meta`） | `saveMeta` 改为 `s.saveSession(meta)`，upsert 一行；启动时 `SELECT` 全部会话 |
| transcript | `sessions/<id>/transcript/chat.jsonl` | `agentCtx.Messages` | 见 6.2 |
| 账本 | `ledger/*.jsonl` | 无 | 插入一行；`scan` 按条件拼 `WHERE`，走索引，按 `at, id` 排序。报表聚合代码不变 |

删除会话（手动删除、删除用户、空会话清理、创建失败回滚）统一走一个函数：在一个事务里删掉 `sessions` 和 `messages` 中的行，再删磁盘目录。

### 6.2 transcript 的增量写入

会话在内存里记三样东西：是否已与库同步、库中已有的条数 `n`、库中最后一条消息的 JSON。每步存档时：

1. 未同步（刚创建，或从未加载过）→ 在一个事务里整体替换。
2. `n` 大于当前条数，或者当前第 `n` 条序列化后与记录不同（发生过压缩等改写）→ 整体替换。
3. 否则只插入第 `n` 条之后的新消息，`seq` 接着编号，`parent_id` 接到上一条。

加载 transcript 时把这三样一并记下。最后一条的 JSON 用"解码后再编码"的结果，保证比较时两边的编码方式一致。

消息的 JSON 与上游 `session.Entry` 里的一致（`json.Marshal(message)`，按 `MessageList` 的方式解码），所以迁移进来的旧消息和新写入的消息格式相同，以后导出回 JSONL 也不会有损失。消息 ID 和时间戳写入后不再改变，历史里显示的时间也就对了。

### 6.3 连接与并发

- **SQLite 只开一个连接**：写入串行，避免 `SQLITE_BUSY`。代价是必须遵守两条规则：
  - 遍历查询结果时，要先把结果全部读完、关掉，再执行别的语句；
  - 事务里只能用事务对象执行语句。

  否则会自己把自己锁死。所有查询都封装成"读完再返回切片"的函数，不对外暴露 `*sql.Rows`。
- **PostgreSQL 连接池上限 10**。实例锁单独占用一个连接，用 `pg_try_advisory_lock(hashtext('pigo-server:' || current_schema()))`。锁的键带上 schema，这样测试时各用各的 schema，互不冲突。
- **时间**：一律存 UTC 的 Unix 纳秒（`BIGINT`）。不用 RFC3339 文本，因为 Go 的 `RFC3339Nano` 会去掉末尾的 0，长度不固定，按字符串比较会出错。
- **布尔值**：存 `INTEGER` 0/1，读出时显式转换，不依赖驱动的隐式转换。

### 6.4 结构升级脚本

两种库共用一套脚本，只用公共子集（`TEXT`、`BIGINT`、`INTEGER`、`DOUBLE PRECISION`、`ON CONFLICT`）。以后真有方言差异时，再按库拆分目录。脚本按分号加换行拆成单条语句执行，不依赖驱动是否支持一次执行多条。每个脚本连同版本记录在同一个事务里执行，两种库的 DDL 都支持事务。

### 6.5 迁移命令与旧文件检测

- **"旧文件"的判定**：以下任意一项存在即算：`auth/auth.json`、`settings.json`、`credentials.json`、`models/models.json`、`ledger/*.jsonl`、`sessions/*/meta.json`、`sessions/*/transcript/`。
- **服务启动时**：有旧文件就拒绝启动，并给出迁移命令。不管库里有没有数据都拒绝，避免新旧两份数据并存、说不清哪份在生效。
- **迁移命令的步骤**：
  1. 打开库。这一步也会加实例锁，所以服务正在运行时迁移会被拒绝。
  2. 确认库为空。
  3. 读出全部旧数据：transcript 用上游 `LoadEntries` 读取，保留消息 ID 和时间戳；账本的坏行跳过并计数；自定义模型空的 `scope` 补为"用户"。
  4. 在一个事务里全部写入。
  5. 提交后，把旧文件按原来的相对路径移到 `legacy/`。
- **移动中途失败**：此时数据已经入库，只是还有旧文件没移走。命令会列出没移走的文件，提示手动移到 `legacy/`。下次启动时，服务的旧文件检测会再次提醒，不会静默出错。
- 迁移不需要 `PIGO_SERVER_SECRET`：密钥是按加密后的记录原样搬运的。

### 6.6 测试

- **测试库辅助函数** `openTestDB(t)`：默认在临时目录建 SQLite 库。`newTestServer` 用它。
- **两种库都跑的测试**：存储层测试用 `forEachDB(t, …)`，SQLite 必跑；设置了 `PIGO_TEST_POSTGRES` 时，再在一个随机 schema 里对 PostgreSQL 跑一遍，结束后删除该 schema。
- **原来直接读写 JSON 文件的测试**：比如"密钥文件里不含明文"，改为检查库中的行。

### 6.7 端到端验证

1. 把真实的 `~/.pigo-server` 复制一份到临时目录，在副本上运行迁移。
2. 核对各类数据的条数。
3. 用副本起一个验证实例。用服务令牌调用管理接口，给一个已有用户重置临时密码（只改副本），再在浏览器里登录，核对历史会话、消息时间、用量面板。

整个过程只动副本，不碰正在运行的 9987 服务和它的数据。

## 7. v2 调整：对话内容回到 JSONL，账本按一轮提交（2026-09-19）

### 7.1 为什么调整

对话内容体量大（工具输出可达几十 KB）、只追加、按会话整份读、几乎不做查询，适合文件；关联关系、元数据和账本需要筛选、聚合和约束，适合数据库。另外希望尽量减少写库和提交的次数。

### 7.2 各类数据的去向

| 数据 | 存放 | 写入时机 |
| --- | --- | --- |
| 用户、登录、密钥、设置与价格表、自定义模型 | SQLite | 改动时立即写（低频） |
| 会话元数据（归属、模型、标题、运行中的一轮、上一轮结果） | SQLite `sessions` 表 | 一轮开始、一轮结束、改设置、打开会话时 |
| 计费账本 | SQLite `ledger` 表 | **一轮结束时**与会话元数据在同一个事务里提交 |
| 对话内容 | `sessions/<id>/transcript/chat.jsonl`（上游格式不变） | 每步追加 |

去掉 `messages` 表（v1 尚未发布，直接修改初始脚本）。

### 7.3 对话内容：真正的追加写

- 仍用上游的文件格式：第一行文件头，其后每行一条消息（`id`、`parentId`、`timestamp`、`message`）。
- 每步存档：已写入的内容没变时，用追加模式把新消息一次写到文件末尾；否则（压缩等改写历史的情况，判断依据同 6.2 的首尾比对）用临时文件加改名整体重写。
- 文件头的 `UpdatedAt` 只在创建和整体重写时更新，追加时不动。服务端不读它，以 `sessions` 表为准。
- 崩溃保护：读取前检查文件末尾，丢弃不完整或解析失败的最后一行（追加写只可能损坏最后一行），最多丢失进行中的那一步。
- 已写入的消息 ID 和时间戳不再改变。

### 7.4 账本：按一轮缓存，结束时提交

- 一轮中每次模型调用的账本行留在这一轮的内存里。页面上的实时费用照常显示，它本来就由用量事件实时累加。
- 一轮结束（完成、出错、停止、到达上限、服务正常退出时被停止）时，在一个事务里写入全部账本行和会话元数据。服务正常退出时先停掉每一轮，所以不会丢。
- 进程崩溃时，正在运行的这一轮的账本行丢失，**不做补记**；对话内容不受影响（每步已追加写入文件）。
- 不属于任何一轮的调用（目前没有，只作兜底）直接写库。
- 一轮进行中，用量报表和管理员汇总不包含这一轮的调用，结束后才出现。
- 结果：每一轮只提交两次（开始时标记"运行中"，结束时提交账本和元数据），和调用次数、步数无关。每步存档只写 JSONL，不写库。

### 7.5 迁移命令

transcript 本来就是 JSONL，原地保留，不导入也不移动。迁移只导入 JSON 小文件和账本，旧文件的检测也不再包括 `sessions/*/transcript/`。

## 8. 草稿会话：发出第一条消息才落盘（2026-09-19）

点「新会话」（包括从场景新建）创建的会话先是**草稿**：只在内存里，`sessions/<id>/` 目录不创建，`sessions` 表不写。

- 草稿能正常打开：读会话、改模型/推理强度、看命令列表、看历史（空）、看工作区（空）都可以；改动留在内存里。
- 第一条消息（`POST /api/sessions/{id}/messages`，包括 `/compact` 和本地回答的命令）到达时 `materializeLocked` 建目录、写入库，之后和普通会话一样。
- 草稿不出现在会话列表里；`sessionJSON` 带 `draft: true`，前端据此不把它加进历史列表。已经停在一个空的普通草稿上时再点「新会话」，不再新建。
- 每个用户最多保留 3 个草稿（`maxDraftsPerUser`），再建时丢掉最早的；草稿不计入 `maxSessions`。服务重启后草稿消失（本来就是空的）。
- 兜底：`upsertSession` 遇到草稿直接返回，任何写库路径（包括服务商改名时批量更新会话）都不会把草稿写进去。
