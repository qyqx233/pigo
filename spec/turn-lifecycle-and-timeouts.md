- 状态：已实现 12.6 的第 1–5 步（2026-09-19）；第 6 步"按进程组取消单条命令"尚未做，取消一条 bash 仍会重启整个沙箱

- 起因：2026-09-19 09:53，会话 `65405ea992f5` 的一轮任务做了 93 次工具调用（46 次 bash），正好在第 10 分钟被 `-request-timeout` 中止。网页只显示 `context deadline exceeded`，bash 报错说"timed out after 5m0s"，但那条命令实际只跑了约 1 分钟。

## 1. 名词

- **一轮（turn）**：用户发一条消息，到 agent 最终停下。期间可能有多次模型调用、工具调用、上下文压缩和重试。
- **一步（step）**：一次模型回复，或一次工具执行。
- **进展**：任何一步开始或结束，或者模型输出了任何内容（文字、思考、工具参数）。

### 2.2 问题清单

| # | 问题 | 后果 |
| --- | --- | --- |
| P1 | 一轮任务挂在 HTTP 请求上 | 超过 10 分钟、刷新页面、电脑休眠、网络抖动，任何一种都会中止整轮，并杀掉正在跑的命令 |
| P2 | 一轮结束才保存 transcript | 服务重启或崩溃时，这一轮的全部记录丢失（文件还在，但模型不知道自己做过什么） |
| P3 | 整轮都持有会话锁 `managed.mu` | 运行期间，同一会话的查历史、查用量、改设置都会排队。表现为刷新页面卡住 |
| P4 | Responses 接口没有看门狗 | 上游挂住时，只能等到整轮时限 |
| P5 | 超时原因报错 | 整轮到期时，bash 仍说是自己超时；网页只显示英文的 ctx 错误 |
| P6 | 取消一条 bash 会杀掉整个沙箱 | 沙箱里的后台进程一起没了，下一条命令要重新启动沙箱 |
| P7 | 长时间无输出时没有心跳 | 前面的反向代理（nginx 默认 60 秒）会先断开连接，又触发 P1 |
| P8 | 只有时间这一种刹车 | 模型陷入循环时烧 token，只能等时间到 |
| P9 | `LastUsed` 只在一轮开始时更新 | 一轮跑满 40 分钟后，沙箱会在它结束后立刻被回收 |

## 3. 目标

1. 一轮任务**在服务端独立运行**，不依赖浏览器连接。只有用户显式点击停止，或触发第 5.2 节的刹车，才会中止。
2. 断线或刷新后能**重新接上**正在运行的一轮，并补发错过的事件。
3. 每完成一步就**落盘**，重启后已完成的步骤一步不丢。
4. 每一层只管自己的时限，**结束原因准确**，用中文告诉用户发生了什么、已完成的部分在哪、下一步能做什么。
5. 一轮运行期间，会话的只读操作不受阻塞。

非目标：同一会话并发跑多轮；跨服务重启继续执行未完成的一轮（重启后该轮标记为"被中断"，可以发"继续"）；多实例部署。

## 5. 设计

### 5.1 一轮任务脱离 HTTP 请求（P1、P3、P7）

新增会话级的**运行中任务**对象 `turnRun`：

```
turnRun {
  id, sessionID, startedAt
  ctx, cancel          // 派生自服务的根 ctx，而不是某个 HTTP 请求
  events  []streamEvent // 本轮全部事件，带递增序号（上限见下）
  status   running | done | failed | canceled | stopped(原因)
  lastProgress time.Time
  subscribers          // 当前连着的浏览器，可以有多个
}
```

- `POST /api/sessions/{id}/messages`：创建 `turnRun`，在后台 goroutine 里执行 `runHostLoop`，然后把当前连接挂成订阅者。连接断开只是取消订阅，不影响任务。
- `GET /api/sessions/{id}/turn`：重新接上。先发一条本轮快照，再实时推送（见 12.3，不再按序号补发）。一轮已结束的，补发完就关闭。
- `POST /api/sessions/{id}/turn/cancel`：停止按钮调用它。前端的 AbortController 只断开自己的订阅，不再代表取消。
- `GET /api/sessions/{id}`：新增字段 `turn: {id, status, startedAt, steps}`。前端打开会话时，发现有正在运行的一轮就自动接上。
- **事件缓冲**（已被 12.3 的快照方案取代）：只保留本轮的事件，结束后再保留 10 分钟供迟到的重连使用。文字增量按条数计，单轮设上限（比如 20000 条），超出后丢弃最早的增量，并告诉重连方"请改从 transcript 加载"。
- **心跳**：订阅流每 20 秒发一个 `{"type":"heartbeat","phase":"bash","elapsed":180}`。前端据此显示"正在执行 bash（已 3 分钟）"，同时让反向代理保持连接。
- **会话锁拆分**：`managed.mu` 只保护元数据，持锁时间是毫秒级。"是否有一轮在跑"由 `turnRun` 表示。发消息时如果已有一轮在跑，返回 409（见 4.7）。
- 回收沙箱时，判断是否有正在运行的 `turnRun`（取代 `busy` 标记）；每次有进展都刷新 `LastUsed`（修 P9）。

### 5.2 刹车与时限（P4、P8）

一轮由一个看守协程管理。它监听进展，按下列规则中止并记下原因：

| 刹车 | 触发条件 | 结束原因 |
| --- | --- | --- |
| 无进展 | 超过 `-turn-idle`（默认 10 分钟）没有任何进展 | `stalled` |
| 总时长 | 超过 `-turn-max`（默认 2 小时） | `time_limit` |
| 步数 | 工具调用达到 `-turn-max-steps`（默认 200） | `step_limit` |
| 用户停止 | 调用了 cancel 接口 | `canceled` |
| 服务退出 | 收到 SIGTERM | `shutdown` |

- **什么算进展**：来自 agent 事件流（模型输出、工具开始/结束、重试通知、压缩）。长时间运行的 bash 本身没有事件，所以只要有一条工具还在执行、没超过它自己的时限，就视为有进展。这样一条合法的 8 分钟编译不会被"无进展"误杀。
- **步数上限要软着陆**：到达上限时，不立即取消，而是在下一步前向模型注入一条系统提示："已达本轮步数上限，请总结当前进度与剩余工作后停止"，再给它一步收尾。收尾也超时才硬停。实现上用 `LoopConfig.ShouldStopAfterTurn` / `GetSteeringMessages` 这两个已有接口，不需要改上游。
- **模型调用的看门狗**：在服务端再套一层 StreamFn 装饰器，和计费装饰器写法相同：若超过 `PIGO_STREAM_IDLE_TIMEOUT`（默认 5 分钟）没收到任何流事件，就取消这一次调用。它对三种接口一视同仁，补上 Responses 接口缺的看门狗，不改上游。取消后按"上游超时"走现有的重试逻辑。

### 5.3 逐步落盘（P2）

- （已被 12.2 取代：`MessageEndEvent` 不覆盖工具结果，改为在 `ShouldStopAfterTurn` 钩子里整体保存。）
- 在 transcript 头部或会话 meta 里记下 `activeTurn: {id, startedAt}`，结束时清除。服务启动时发现残留的 `activeTurn`，就给这一轮补一条说明："本轮因服务重启中断，已完成 N 步，可发送'继续'"，并在网页上显示。

### 5.4 工具层（P5、P6）

- **超时原因分清**：bash 的 `runCtx` 到期时，判断父 ctx 是否也已结束：
  - 父 ctx 未结束，是命令自己超时：`命令超过 <t> 未完成，已终止`
  - 父 ctx 已结束，是整轮被中止：`本轮已中止（<原因>），命令被终止`
- **取消单条命令而不杀沙箱**：现在的控制协议是"往沙箱里的 shell 写一个脚本，读到结束标记"。脚本改为先打印子进程组 id，再等它退出。取消时，宿主机按进程组发 `SIGTERM`，过 3 秒再发 `SIGKILL`，然后读到结束标记，shell 继续可用。只有协议本身出错时才重启沙箱。**需要先验证**：`--unshare-pid` 下沙箱内看到的 pid 和宿主机不同，要么从宿主机侧通过 `/proc/<bwrap子进程>/task/*/children` 找到进程组，要么由沙箱内的一个小守护进程代为发信号。实现前用原型确认选哪种。
- 默认时限不变：bash 默认 2 分钟、上限 10 分钟，由模型自己设。

### 5.5 提示文案（P5）

| 结束原因 | 网页显示 |
| --- | --- |
| `stalled` | 本轮已中止：超过 10 分钟没有任何进展。已完成 N 步，结果已保存，可以发送"继续" |
| `time_limit` | 本轮已中止：运行超过 2 小时上限。已完成 N 步…… |
| `step_limit` | 本轮已达 200 步上限，模型已总结进度。发送"继续"可接着做 |
| `canceled` | 已停止。已完成 N 步，结果已保存 |
| `shutdown` | 服务重启，本轮中断。已完成 N 步…… |
| 上游错误 | 保持现有的分类错误信息（重试耗尽等） |

原因字段也写进服务端日志，便于事后排查。

## 6. 前端改动

- 发消息：用 POST 建立一轮并订阅。点停止时调用 cancel 接口，而不是只断开连接。
- 打开或刷新会话时，如果 `session.turn.status == running`，自动调用 `GET /turn` 接上（通过 `thread.resumeRun`），把快照和后续事件渲染到最后一条回复里。
- 连接意外断开时自动重连（重新拿快照），期间显示"连接中断，正在重连……"。
- 运行状态提示条：显示当前在做什么、已运行多久、第几步（来自心跳和工具事件）。
- 结束原因按第 5.5 节显示，并附一个"继续"按钮（等同于发送"继续"）。

## 10. 实施顺序

每个阶段都可以单独发布，前一个阶段的收益不依赖后一个。

1. **止血**（小改动，立刻见效）：5.4 的超时原因区分；5.5 的文案；5.2 的模型看门狗装饰器；心跳；`LastUsed` 在有进展时刷新。
2. **逐步落盘**（5.3）：重启不再丢记录。
3. **脱离请求**（5.1）加会话锁拆分，以及前端的重连与取消。这是最大的一步。
4. **刹车**（5.2）：无进展、总时长、步数上限，替换 `-request-timeout`。
5. **单条命令取消而不杀沙箱**（5.4 后半），先做原型验证。

## 11. 风险

- **任务不再因断线而停**：用户关掉页面后，一轮仍会继续烧 token，直到完成或触发刹车。所以阶段 3 必须和阶段 4 一起上线，不能只做脱离请求而不做刹车。
- **内存**：事件缓冲按轮保存并设了上限。结束 10 分钟后释放。
- **transcript 追加与整体保存交替**：压缩后的整体保存必须覆盖掉之前的追加，要测这种交错情况。
- **进程组取消**依赖 pid 命名空间的细节，所以放到最后一个阶段，并且先做原型。

## 12. 实现细化（编码前核实代码后的结论）

### 12.1 核实到的事实

| 事实 | 位置 | 对设计的影响 |
| --- | --- | --- |
| `MessageEndEvent` 只对 assistant 消息触发；工具结果、注入的消息是 loop 协程直接追加到 `agentCtx.Messages`，没有事件 | `runtime/stream_response.go:118`、`loop.go:256` | 不能靠事件逐条追加 transcript |
| `afterTurn` 在 loop 协程上依次调用 `GetSteeringMessages` → `PrepareNextTurn` → 压缩 → `ShouldStopAfterTurn`，此时消息列表稳定 | `loop.go:306-329` | 落盘和步数刹车都挂在这两个钩子上 |
| 服务端当前没有设置这些钩子（只有调度器可能设 `GetFollowUpMessages`，服务端未启用） | `cli/run/run.go:598` | 可以直接使用；为稳妥起见，已有钩子要包一层而不是覆盖 |
| 重试只在"还没吐出内容"时发生，判断依据是 `provider.IsTransient(err)`，错误可以用 `Transient()` 方法自报 | `runtime/retry.go:103`、`provider/errors.go:133` | 看门狗报一个自报可重试的错误；已经吐出内容后卡住则整轮以错误结束（与现有行为一致） |
| bash 工具读 `managed.live` 不加锁，靠的是整轮都持有会话锁 | `sandboxbash.go:75` | 拆锁时必须改成加锁取出沙箱指针 |
| 删除会话、删除用户、进程退出都会直接 `stopLive` | `main.go:496`、`users_api.go:207`、`main.go:771` | 改成先取消本轮、等它收尾，再停沙箱、删文件 |
| 前端 `thread.reset` 不会中止正在跑的本地运行；本地 `cancelRun` 与"停止"用同一种 `AbortError(false)` | assistant-ui `local-thread-runtime-core.js` | 停止按钮改为显式调用服务端取消接口；本地 abort 一律只表示"断开订阅" |
| LocalRuntime 支持 `thread.resumeRun({parentId, stream})`，可以传入自定义的流生成器 | 同上 `:282` | 打开会话时用它接上正在运行的一轮 |

### 12.2 逐步落盘：用钩子做整体保存

- 在 `ShouldStopAfterTurn` 钩子里（loop 协程，消息稳定），用 `Store.Save` 整体写一次 transcript（临时文件加改名，原子替换）。这样压缩后的重写自然被覆盖，不存在追加与整体保存交替的问题（替代第 5.3 节"追加 + 压缩后整体保存"的做法）。
- 一轮开始、把用户消息追加进上下文后，立即保存一次。
- 代价是每一步重写整个文件（目前最大的会话约 670KB），可以接受。以后如果成为瓶颈，再改成"未压缩时追加"。
- 同一个钩子里更新 `meta.activeTurn.steps` 并保存 meta。

### 12.3 turnRun 的形态

- **不保存事件日志，改用快照**：turnRun 维护本轮的物化状态，包括累计文字、各次调用的用量、当前阶段（哪个工具在跑、从何时开始）和步数。
  - 接上时先发一条 `snapshot`，再推送之后的实时事件。
  - 生成快照和登记订阅者在同一把锁下完成，所以不会漏也不会重。
  - 这样事件缓冲不会无限增长，第 5.1 节的"事件条数上限"不再需要。
- **每个订阅者一个带缓冲的通道**（容量 256）。写满说明订阅者太慢，服务端关闭它；前端会走断线重连，拿到新的快照。慢速和断线用同一条恢复路径。
- **心跳由订阅协程自己的计时器产生**，不写进状态，也不算进展。
- **结束原因**用 `context.WithCancelCause` 传递。原因是几个哨兵错误：`stalled`、`time_limit`、`canceled`、`shutdown`、`session_deleted`。`step_limit` 属于正常结束，另外单独标记。
- **提示文案由服务端生成**（中文），写在最终事件的 `error` 或 `notice` 字段里，同时带上 `reason` 和 `steps` 供前端决定是否显示"继续"按钮。
- **无进展看守**：每 5 秒检查一次。有工具在执行时，阈值放宽到 `max(-turn-idle, bash 上限 10 分钟 + 1 分钟)`，避免把合法的长命令当成卡死。

### 12.4 锁的纪律

`managed.mu` 只保护这些内容：`meta`、`closed`、`live` 指针、`turn` 指针、`runCfg`、`agentCtx` 指针的赋值。都是毫秒级持有，唯一例外是启动沙箱时最多 5 秒的探活。

| 操作 | 做法 |
| --- | --- |
| 开始一轮 | 加锁：准备 agent 上下文、追加用户消息、复制一份 `runCfg` 并挂上本轮的钩子、登记 `turn`、写 `activeTurn`；解锁后在后台协程运行。运行期间 `agentCtx` 只由本轮协程使用 |
| bash 工具 | 加锁取出（必要时启动）沙箱，解锁后执行命令 |
| 修改会话设置 | 照常修改 meta 和 `runCfg`；正在跑的一轮用的是自己的副本，下一轮生效 |
| 删除会话或用户、进程退出 | 加锁标记 `closed`，取消本轮；解锁后最多等 10 秒让它收尾；再停沙箱、删文件。本轮收尾时发现 `closed` 就不再写盘 |
| 回收空闲沙箱、清理空会话 | 用"是否有一轮在跑"取代原来的 `busy` 标记 |
| 刷新 `LastUsed` | 有进展时最多每 30 秒一次，加锁改内存，本轮结束时一并保存 |

### 12.5 历史与接上的配合

- 一轮运行期间，历史接口不返回这一轮在用户消息之后产生的内容，这部分由接上时的快照提供，避免同一段内容出现两次。分界点是本轮开始时用户消息在 transcript 中的位置；发生过压缩就不再裁剪。
- 会话信息增加 `turn`（运行中或刚结束的一轮，保留 10 分钟）和 `lastTurn`（持久化的上一轮结果，包括因重启而中断的）。

### 12.6 编码顺序

1. `stallguard.go`（模型调用看门狗）、bash 超时原因区分。两者都独立，可以单独测试。
2. `turnrun.go`：状态、快照与订阅、看守协程、结束原因、步数钩子、落盘钩子。用假的 loop 做单元测试。
3. 接线：发消息、接上、取消三个接口；锁的纪律；`activeTurn` / `lastTurn` 与重启恢复；进程退出流程；新的启动参数。补集成测试。
4. 前端：发送即订阅；打开会话时用 `resumeRun` 接上；停止按钮改调取消接口；断线重连；运行状态条；结束原因与"继续"按钮。
5. 用一个慢速的假 LLM 端点手工验证端到端。
6. 按进程组取消单条命令：另起原型，不阻塞前五步。

## 13. 看门狗的「进展」定义与调用可观测性（bug 驱动）

**这一节是一次线上故障倒逼出来的，不是设计推演。**

- **故障**：2026-09-21，会话 `f35a2997` 的一轮任务在拿齐资料后，最后一次综合作答的模型调用 **6 分 05 秒一个字都没产出**，5 分钟的模型调用看门狗**没有触发**，最后由用户手动点停止。账本证据：该次调用 `status=aborted, input=0, output=0`，与上一行相差 372 秒（> 5 分钟）。
- **根因**：第 5.2 节把调用看门狗定义为「超过阈值**没收到任何流事件**」，而第 1 节对「进展」的定义是**模型输出了内容**。两个定义不一致。`relayGuarded` 对**每一个**事件都 `timer.Reset`，所以上游只要持续送无内容的事件（心跳、空 delta），计时器就一直往后推，调用可以永远挂着不被中止。
- **改动 A（语义对齐）**：看门狗只在**改变消息内容**的事件上重置计时器（text / thinking / toolCall），与第 1 节的「进展」一致。另加一条**首字节死线**：一次调用在产出第一个内容事件之前，用更短的时限（默认 2 分钟）——几分钟吐不出第一个 token 的调用基本已经挂了，而且它没有产出、可以安全重试。
- **改动 B（可观测性）**：根因只能靠排除法推断，因为**落盘数据里没有任何一个字段能说明「上游到底有没有回东西」**。**异常结束的每次模型调用**（stalled / aborted / error）往服务日志写一行计数，正常结束不写：

  ```
  call f35a2997/3a273ca3 chat model=global:hy3: stalled after 2m0s:
    events=612 progress=0 first=- max_gap=1.4s limits=2m0s/5m0s
  ```

  `events` 大而 `progress=0`，就是「上游一直在送东西但一个字都不是内容」的签名——今天这一行就能直接定案。

  **不进账本**：账本是钱的表，诊断计数混进去是职责不清，而且要为四个数字动 sqlite + postgres 两套迁移，代价高于价值。**不做原始事件轨迹**（2026-09-21 决定）：等出现第二个「靠计数也说不清」的案例再说。

原则：**落盘的是调用的体检指标，不是事件轨迹**。重放对话有 transcript，计费有 tokens/cost，这一行日志只回答三个问题——上游有没有回、回的是内容还是心跳、最长静默多久离阈值差多少。绝不记录消息内容和请求头（provider 的 key 在请求头里）。

### 13.1 实现（2026-09-21 已完成）

| 位置 | 内容 |
| --- | --- |
| `stallguard.go` `progressSize` | 把「进展」定义成消息**长度增加**，而不是收到事件。心跳和空 delta 因此不再续命 |
| `stallguard.go` `relayGuarded` | 两级死线：产出第一个内容前用 `firstByte`，之后用 `idle`；异常结束写一行 `callReport` |
| `stallguard.go` `streamFirstByteTimeout` | 默认 2 分钟，`PIGO_STREAM_FIRST_BYTE_TIMEOUT` 可覆盖，且不超过 idle 阈值 |
| `guardStream(inner, idle, label)` | 多一个 label（chat / compaction / subagent），只用于日志那一行 |

零产出的调用被中止时仍标记为可重试（`Transient`），因为没有任何内容到达用户，重发是安全的。重试预算是每次运行 3 次、指数退避封顶 1 分钟，所以最坏挂起时间由原来的 4×5 分钟缩短为 4×2 分钟。

**压缩调用不适用首字节死线**：它把整个历史发上去，首个 token 本来就是所有调用里最慢的，而且中止它会直接毁掉这一轮。`guardStream` 的 `firstByte` 参数由调用点显式传入，压缩传 `idle` 即等于放弃这条死线。

### 13.2 四个数字，谁先响

**写这一节前漏看了一件事：传输层本来就有内容失速看门狗。** `internal/provider/transport.go` 的 `pump` 有双看门狗，第 5.2 节只提了它的 idle 那一个。结果是内容失速在服务端被重新实现了一遍。**这个漏看本身要记下来**，否则下一个人还会重复踩。

| 层 | 条件 | 阈值 | 覆盖范围 |
| --- | --- | --- | --- |
| 服务端守卫 | 从未产出内容 | **2 分钟**（压缩豁免） | 所有驱动 |
| 服务端守卫 | 有过内容后不再增长 | 5 分钟 | 所有驱动 |
| 传输层 idle | 一个字节都没收到 | 5 分钟 | Chat Completions / Anthropic |
| 传输层 stall | 收到字节但没有内容 | idle×1.2 = 6 分钟 | 同上 |

- **服务端那层永远先响**，传输层是兜底。
- **不要把服务端那层当重复实现删掉**：`openai.go` 和 `anthropic.go` 是 `transport.go` 的 Decoder，由它的 `pump` 驱动，所以有双看门狗；而 `responses.go` 有自己的 `pump`（走 OpenAI SDK），全文没有任何计时器。**对 Responses 驱动，服务端这一层是仅有的一层**。首字节死线更是上游完全没有的能力。
- 两层的关系是：对 Chat Completions / Anthropic 是**重叠**（服务端先响），对 Responses 是**唯一**。
- 两层对「内容」的判据一致：**消息变长**才算进展。
- **仍未被覆盖的洞**：`inner()` 在返回流之前就卡住（连接或响应头挂起）时，两层的计时器都还没起跑，只有轮次级的 `-turn-idle` 管得着。本次不修，记在这里。

这次故障的时间线正好把这张表验证了一遍：传输层 idle（5 分钟）没响 ⇒ 字节一直在到；传输层 stall（6 分钟）还差 5 秒没到 ⇒ 那 6 分钟确实没有内容；用户在 6 分 05 秒手动停止。**两个计时器一个响一个没响，交叉印证了「心跳续命、内容为零」**，不再是排除法推断。

**一个顺带的发现**：原有的 `TestStallGuardLeavesProgressingCall` 连发十个**空**的文本事件来模拟「正在产出的调用」——那恰恰是本次故障的形状。测试一直在为这个 bug 背书。已改成让消息真的增长，并新增 `TestStallGuardIgnoresContentlessEvents` 锁住新语义。
